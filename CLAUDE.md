# Claude Development Guidelines

## Project Overview

`@postalsys/email-ai-tools` is a Node.js library that analyzes one parsed email
at a time with an OpenAI-compatible chat model: a summary, the sentiment, whether
a reply is expected, a fraud risk score, and the events and actions the message
mentions. It also lists the models an endpoint serves. Version 2.0 dropped the
risk-only analysis, the embeddings and the question answering over stored email,
which lost their only consumer when EmailEngine removed its Document Store.

It is published to npm and consumed by other Postal Systems projects - most
notably EmailEngine (`../emailengine`), where it ships inside a standalone binary
built with `@yao-pkg/pkg`. See **Platform constraints** below; it constrains
which dependencies this library may use.

## Project Structure

- `src/index.ts` - Public entry point; declares the members listed below as its own constants
- `src/lib/` - Implementation modules (one feature per file)
- `src/package-info.ts` - Generated by `scripts/build.js` from `package.json` (name and version,
  for the User-Agent). Gitignored, regenerated by `npm run build` and `npm run typecheck`. Never
  import `package.json` from `src/`.
- `scripts/build.js` - The build (see TypeScript layout)
- `dist/` - Build output, gitignored; it is what gets published to npm
- `/test` - Tests using the Node.js native test runner (`*.test.cjs`), run against `dist/`
- `/test/package/` - Checks of the built package: `cjs-smoke.test.cjs` (CommonJS shape and a full
  summary through the CommonJS graph) and `package.test.mjs` (ES module build, packed file list,
  consumers type-checked against the built declarations)
- `/test/helpers/mock-server.cjs` - Local mock of the OpenAI-compatible API used by tests
- `/examples` - Standalone usage examples (`*.cjs`, run them after a build)

### Library Modules

- `src/lib/generate-summary.ts` - `generateSummary()` plus `DEFAULT_SYSTEM_PROMPT` /
  `DEFAULT_INSTRUCTIONS` / `DEFAULT_MODEL`; returns `{ result, usage }`, where
  `result` is the model's JSON object (documented properties normalized, custom
  ones passed through) and `usage` the request id, model, token counts and time.
  The instructions and the input format description go in the system message,
  the email alone goes in the user message as one JSON object with decoded
  headers. A parameter the backend refuses with a 400 naming it
  (`response_format`, `reasoning_effort`, `temperature`, `top_p`) is dropped,
  retried and remembered per endpoint and model; reasoning models
  (`isReasoningModel()`) get `reasoning_effort: "low"` unless told otherwise.
- `src/lib/visible-text.ts` - drops hidden elements, scripts, styles and comments
  from HTML and invisible characters from text, so the model reads what the
  recipient sees.
- `src/lib/signals.ts` - checks run in code before the model sees the email
  (executable attachments, link text naming another host than its target,
  lookalike domains, display name and reply address mismatches, verified
  authentication failures, removed hidden content), passed to the model as
  `signals` and applied afterwards as a floor on `riskAssessment.risk`.
- `src/lib/authentication.ts` - parses the topmost Authentication-Results header
  into an `authentication` block marked verified when its authserv-id is one
  the caller trusts (`trustedAuthservIds`, `acceptUnnamedAuthentication`).
- `src/lib/list-models.ts` - `listModels()`; lists the chat models an endpoint
  serves, newest family first (`chatOnly: false` keeps the rest), each with a
  description and a recommended flag (`describeModel()`).
- `src/lib/api-request.ts` - shared HTTP request helper (size cap, JSON parsing, 429
  retry with Retry-After, error shaping) used by every API call.
- `src/lib/token-estimate.ts` - character-based token estimate and prompt fitting against
  a budget that covers the fixed parts of the prompt too.

## Technology Stack

- **Runtime**: Node.js >= 20 (CI tests on 20, 22, 24 and latest).
- **Language and module system**: TypeScript under `src/`, published as a dual package: ES modules
  in `dist/esm/` and CommonJS in `dist/cjs/`, each with type declarations (see TypeScript layout).
- **HTTP**: `undici` (`fetch` + `Agent`) for all outbound API calls.
- **Token budgeting**: a character-based estimate in `src/lib/token-estimate.ts` (no
  tokenizer dependency); the model's own context-length error is the backstop.
- **Email/text helpers**: `@postalsys/email-text-tools` (HTML to text),
  `libmime` (decoding encoded words in header values), `htmlparser2` with
  `domutils` and `dom-serializer` (hidden element removal and link extraction,
  pinned to their last CommonJS majors) and `tldts` (registrable domains).

## Development Commands

```
npm run build           # Produce dist/ (also runs on install and before publish via `prepare`)
npm test                # Build, then run the test suite against dist/
npm run test:cjs        # Build, then the CommonJS suite with require(esm) disabled (CommonJS graph guard)
npm run test:coverage   # Run the suite under c8 coverage
npm run typecheck       # Generate src/package-info.ts, then tsc -p tsconfig.json
npm run lint            # typecheck, then eslint .
npm run lint:fix        # eslint . --fix
npm run format          # prettier --write .
npm run format:check    # prettier --check .
npm run update          # Refresh deps: remove node_modules + lockfile, ncu -u, npm install
```

Run a single test file, or a single test by name:

```
node --test test/signals.test.cjs
node --test --test-name-pattern="lookalike" test/*.test.cjs
```

(build first, the tests load `dist/`). ESLint uses the shared Postal Systems flat config in its
TypeScript form (`eslint.config.js`, `../nodemailer/eslint.config.js` and
`../pubface/eslint.config.js` are the canonical form, kept identical except the "Repo-specific"
block, which here turns off `no-await-in-loop` for the intentional sequential retry loops).
Prettier options live in `.prettierrc.cjs`. CI (`.github/workflows/test.yaml`) runs lint
(typecheck included), format:check and the tests on every matrix job, plus `npm run test:cjs` on
22 and later.

## TypeScript layout

- `scripts/build.js` generates `src/package-info.ts`, compiles `src/` with `tsconfig.esm.json`
  into `dist/esm` and with `tsconfig.cjs.json` into `dist/cjs`, writes a `package.json` pinning
  the module format into each, and appends one line to `dist/cjs/index.js` (see below).
  `tsconfig.base.json`: strict, `exactOptionalPropertyTypes`, `erasableSyntaxOnly`,
  `isolatedModules`. `tsconfig.json` is the type-check. `@types/node` stays on 20.x and
  `typescript` on 6.x (`.ncurc.cjs`). The layout follows `../pubface` and `../nodemailer`.
- **Every requireable path of the pre-TypeScript package still resolves**: the `exports` map serves
  `.`, `./index`, `./index.js`, `./lib/<name>` and `./lib/<name>.js` (ES module build for
  `import`, CommonJS for `require`) and `./package.json`; `typesVersions` maps the `lib/*` paths
  for `node10` type resolution.
- **The CommonJS shape is the pre-TypeScript one.** `require('@postalsys/email-ai-tools')` returns
  the ten members as plain writable enumerable properties, which is why `src/index.ts` declares
  each as `export const` instead of re-exporting it (tsc compiles a re-export to a getter). The ES
  module entry also has a default export object with the same members, for
  `import emailAiTools from '@postalsys/email-ai-tools'`; in the CommonJS build the build points
  `default` at the exports object itself, non-enumerable, so the enumerable keys stay the ten. The
  `lib/` modules have named exports only, as before (their key order now lists constants before
  functions, which is how tsc emits them).
- Source in `src/` uses ES module syntax only (no `require`, `module`, `__dirname`,
  `import.meta`, JSON imports), relative imports carry the `.js` extension, Node builtins use the
  `node:` prefix. Every optional property of a public interface carries an explicit `| undefined`
  so consumers compiling with `exactOptionalPropertyTypes` can pass a value that may be undefined.
- The tests stay plain CommonJS (`*.test.cjs`) and load the package by name
  (`require('@postalsys/email-ai-tools/lib/signals')`), through the `exports` map.

## Testing

- Uses the Node.js native test runner with the native `assert` module.
- Tests live in `/test` and must be named `*.test.cjs` (`test/package/` also has `*.test.mjs`) -
  the runner globs only match those, so helpers (e.g. `test/helpers/mock-server.cjs`) are never
  picked up as test files.
- Tests are hermetic: they run against the in-process mock server in
  `test/helpers/mock-server.cjs` rather than calling real OpenAI endpoints. Do not
  add tests that require live API credentials or network access.
- Run `npm test` before committing and make sure it passes.

## Platform constraints (important)

- **Node.js 20 is the minimum supported version** (`engines.node` is
  `>=20.0.0`). Runtime code, tests and tooling must work on Node 20, 22 and 24.
- **Everything that reaches runtime must be genuinely CommonJS-loadable.**
  EmailEngine bundles this library into a single executable with
  `@yao-pkg/pkg`, which snapshots the CommonJS `require` graph at build time and
  cannot load ES modules. `require()` of this package and of every runtime
  dependency must work with `--no-experimental-require-module`: Node 22+ (and
  20.19) enable require(esm) by default, which hides an ESM-only dependency
  until the pkg binary fails. A CommonJS entry that only wraps a dynamic
  `import()` of ESM code does not count.
- **Keep the dual build.** Never drop the CommonJS output or make the CommonJS entry depend on
  ESM-only syntax.
- **How to check:** `npm run test:cjs` runs the whole CommonJS suite under
  `NODE_OPTIONS=--no-experimental-require-module`; CI runs it on Node 22 and later.
  `test/commonjs-graph.test.cjs` requires every runtime dependency, including the
  jsdom-backed `mimeHtml` of `@postalsys/email-text-tools` that the summary code
  never loads, so the guard sees the whole graph.
- **Pins:** never add or upgrade to an ESM-only dependency. Hold the last
  CommonJS major in `.ncurc.cjs` (`reject` or `target`) with a one-line comment
  explaining why; `npm run update` honors it. `nanoid`, `htmlparser2` (10.x),
  `domutils` (3.x), `dom-serializer` (2.x) and `@asamuzakjp/css-color` are
  rejected; `undici` is held to the 7.x line by `target` (8.x requires
  Node >= 22.19). When `npm run update` proposes an upgrade, confirm
  `npm run test:cjs` still passes before accepting it.
- **The jsdom chain:** `@postalsys/email-text-tools` -> jsdom -> cssstyle ->
  `@asamuzakjp/css-color` >=4.1.2 pulls in `@csstools/*` v4, which are pure
  ESM. `package.json` `"overrides"` holds `@asamuzakjp/css-color` at 4.1.1 so
  this repo's own tests and CI exercise the CommonJS graph. Overrides do not
  propagate to consumers: an app installing this package resolves css-color
  itself, and EmailEngine carries its own identical override and `.ncurc.js`
  reject.

## Dependency Management

- Use `npm run update` to bump dependencies (it runs `ncu -u` then a clean
  install). Respect the `reject` list in `.ncurc.cjs`.
- After updating, run `npm test`, `npm run lint`, and `npm run format:check`
  to confirm nothing broke.
- Keep `package.json` versions exact (no `^`/`~` ranges), dev dependencies
  included, to match the existing convention and keep `pkg` builds reproducible.

## Versioning & Releases

- Releases are automated with **release-please** (`.github/workflows/release.yaml`).
  Merging Conventional Commit messages to `master` opens/updates a release PR;
  merging that PR tags the version, updates `CHANGELOG.md`, and publishes to npm
  with provenance.
- Commit prefixes drive the version bump: `fix:` -> patch, `feat:` -> minor,
  `feat!:` / `BREAKING CHANGE:` -> major.

## Code Style Rules

- TypeScript with ES module syntax under `src/`, compiled to both formats (see TypeScript
  layout). Plain JavaScript files outside `src/` follow the package `"type": "module"`, except
  `.cjs` files (configs, tests, examples).
- Never use emojis in code or documentation; printable ASCII characters only.
- Use a single hyphen-minus (`-`) as a dash in user-facing strings and docs.
  Never use double hyphens (`--`), em dashes, or en dashes.
- Formatting is owned by Prettier and linting by ESLint - run both before
  committing; do not hand-format against them.
- **Git commit messages: do not list Claude (or any AI) as a co-author or
  contributor.** Write commit messages in the project's own voice.
- Use Conventional Commit prefixes so release-please works (`fix:`, `feat:`,
  `chore:`, `docs:`, `test:`, `ci:`, `refactor:`).
- For commits that do not change runtime behavior (docs, comments, CI/workflow
  tweaks, formatting), append `[skip ci]` to the commit message to avoid
  triggering the GitHub Actions workflows. Exception: do not add `[skip ci]` to
  commits using a `fix:` or `feat:` prefix - those must run so the release action
  is triggered.

## Workflow After Making Changes

1. Run `npm run format` and `npm run lint`.
2. Run `npm test` and confirm it passes.
3. Review changed code for reuse, quality, and efficiency (`/simplify`), and run
   `/security-review` for anything touching parsing, prompts, or outbound HTTP.
4. After pushing, check the GitHub Actions runs (e.g. `gh run list --branch master`)
   and report their status, including the CodeQL ("code quality") results. If a
   run fails for an unrelated infrastructure reason (checkout reporting "account
   suspended", HTTP 403, other auth errors), check https://www.githubstatus.com/
   for an active GitHub incident before assuming the code is at fault.
